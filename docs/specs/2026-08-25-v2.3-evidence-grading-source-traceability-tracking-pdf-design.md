# 研擎 V2.3 设计：证据可信度、来源追溯、触发器精确证据与 PDF 阅读体验

> 更新时间：2026-08-25
> 状态：待评审
> 范围：证据分级/置信度、公告原文浏览与来源追溯、跟踪触发器连接精确证据、PDF 分页与阅读体验优化
> 前置：建议先处理容器测试文件与镜像同步（需用户确认部署）

## 1. 背景与目标

当前研擎已经具备：

- CNINFO 公告/定期报告采集、PDF 下载、文本抽取、摘要证据库。
- `evidence_digest`、`financial_traceability`、`contradiction_matrix`、`tracking_dashboard`、`research_judgement`。
- 服务端 Chromium 渲染 PDF 导出。

用户希望下一阶段把研擎从“能看证据”升级为“能判断证据可信度、能点回原文、能跟踪精确证据、能舒适阅读/导出”。

### 目标

1. **证据分级 / 证据置信度**：每条证据和摘录都有来源类型、证据等级、置信度，AI 与前端都优先展示可追溯的高等级证据。
2. **公告原文浏览与来源追溯增强**：用户可以从摘要、矩阵、跟踪看板、证据链直接打开原始 PDF/文本，并看到页码、日期、来源 URL、证据 ID。
3. **跟踪触发器连接精确证据**：每个跟踪项不再只是文字，而是绑定到具体的 `evidence_id`、引用句、页码和等级。
4. **PDF 分页与阅读体验优化**：导出 PDF 按研究章节稳定分页，卡片不跨页断裂，长证据列表可读性更好。

### 非目标 / 边界

- 不接入 cnstock API、不读取 cnstock 数据、缓存、Cookie、数据库或报告资产。
- 不改变 BrianHub SSO、网关路由、门户 AI 配置边界。
- 不新增需要密钥的私有数据源。
- 不输出买入、卖出、加仓、减仓等直接交易指令。
- 不把脆弱爬虫作为核心依赖；当前仍以 CNINFO 为唯一公开公告源，其他源保留为未来适配器边界。

## 2. 现状与关键数据模型

当前后端核心模型（`backend/app/main.py`）：

```python
class EvidenceSnippet(BaseModel):
    quote: str = ""
    note: str = ""
    page: int | None = None

class EvidenceRecord(BaseModel):
    evidence_id: str
    ticker: str
    source: str = "cninfo"
    source_label: str = "CNINFO 公告原文"
    title: str
    announcement_date: str = ""
    category: str = "other"
    url: str = ""
    local_pdf_path: str = ""
    local_text_path: str = ""
    download_status: str = "skipped"
    text_extract_status: str = "skipped"
    snippet_count: int = 0
    text_length: int = 0
    snippets: list[EvidenceSnippet]
    data_gaps: list[str]

class TrackingDashboardItem(BaseModel):
    trigger: str
    status: str  # watch | data_insufficient | confirmed | invalidated
    why: str
    evidence: list[str]
    next_check: str
    invalidate_if: str
```

当前 `evidence`、矩阵、跟踪看板中的证据主要是纯文本 `list[str]`，缺少：

- 证据等级 / 来源类型 / 置信度。
- 稳定 `evidence_id` 引用。
- 页码、来源 URL、文件名的结构化追溯。
- 从 UI/PDF 跳回原文的入口。

另外，当前 `extract_pdf_text` 把 PDF 所有页文本直接拼接，`EvidenceSnippet.page` 基本为 `None`；V2.3 需要保留分页信息，才能实现“点回原文第几页”。

## 3. 总体设计

### 3.1 证据分级与置信度

#### 3.1.1 来源类型

新增 `source_type` 枚举，当前至少支持：

| source_type | 中文 | 说明 | 典型等级 |
|---|---|---|---|
| `official_financial_report` | 正式定期报告 | 年报/半年报/季报、审计后数据 | A |
| `official_announcement` | 公司公告 | 业绩预告、合同、中标、质押、回购、风险提示等 | B |
| `exchange_reply` | 交易所问询/回复 | 问询函、关注函、回复函 | B/C |
| `policy` | 政策/预算 | 政策原文、预算文件 | B |
| `tender_order` | 招标/订单 | 中标公告、订单公告 | B |
| `industry_data` | 行业数据 | 行业协会/第三方统计 | C |
| `media_news` | 媒体报道 | 新闻、自媒体 | C/D |
| `ai_inference` | AI 推断 | 无原文支撑的分析性内容 | D |
| `unknown` | 未知/未分类 | 无法判定来源可信度 | D |

当前实际只采集 CNINFO，因此默认：

- `annual_report` / `semiannual_report` / `quarterly_report` -> `official_financial_report`
- `forecast` / `contract` / `pledge` / `risk` / `other` -> `official_announcement`
- 未来新适配器再扩展为政策、订单、交易所回复等类型。

#### 3.1.2 证据等级

每个 `EvidenceRecord`、`EvidenceSnippet`、摘要项、矩阵证据项、跟踪证据项新增：

```python
class EvidenceGrade(str, Enum):
    A = "A"  # 官方定期报告/审计后财务数据
    B = "B"  # 公司正式公告
    C = "C"  # 问询回复、行业数据、媒体等较不可直接采信
    D = "D"  # 无法追溯/AI 推断/数据不足
```

等级计算规则（后端函数 `grade_evidence_record(item)`）：

1. 没有 `evidence_id`、`url` 或 `announcement_date` -> 不得高于 `C`，缺关键字段记 `D`。
2. 根据 `category` 和 `source_type` 给基础等级。
3. 若 `download_status != "downloaded"` 或 `text_extract_status != "ready"`，最高降一级；无文本只能用于标题级线索，不得作为深度引用。
4. 若 `data_gaps` 包含“下载失败”“提取失败”等，标记为 `C/D` 并进入 `data_gaps`。
5. 具体映射：

| 条件 | grade | confidence |
|---|---|---|
| 定期报告 + 已下载 + 已抽取 | A | high |
| 定期报告但未抽取到文本 | B | medium |
| 公司公告 + 已下载 + 已抽取 | B | high |
| 公司公告但只有标题/URL | C | medium |
| 问询/行业/媒体（未来源） | C | low/medium |
| 无法追溯 / AI 推断 / 数据不足 | D | low |

#### 3.1.3 置信度

`confidence` 取值 `high` / `medium` / `low`，由以下因素综合：

- 证据等级。
- 是否可打开原文 PDF。
- 是否有页码。
- 是否与 AI 引用句完全匹配（服务端校验）。
- 是否有反证/缺口。

新增 `EvidenceConfidence` 对象：

```python
class EvidenceRef(BaseModel):
    evidence_id: str = ""
    source_label: str = ""
    quote: str = ""
    page: int | None = None
    source_url: str = ""
    source_date: str = ""
    grade: str = "D"
    confidence: str = "low"
    field: str = ""          # 可选：财务字段/主题
    logic: str = ""          # 可选：该证据如何支持当前论断
```

#### 3.1.4 对现有数据结构的兼容

- `EvidenceRecord` 增加可选字段：`source_type`、`grade`、`confidence`、`retrieved_at`、`file_name`。
- `EvidenceSnippet` 增加：`grade`、`confidence`、`source_url`、`source_date`、`page_label`。
- `EvidenceLibrary.summary` 增加 `grade_summary`：`{"A": n, "B": n, "C": n, "D": n}`。
- `EvidenceDisplay` 的 `EvidenceItem` 增加 `EvidenceRef` 字段，同时保留 `quote` / `note` 文本，保证历史报告仍可渲染。
- `ContradictionMatrixRow` 保留 `supporting_evidence` / `opposing_evidence` 字符串数组，同时新增 `supporting_evidence_refs` / `opposing_evidence_refs`。
- `TrackingDashboardItem` 保留 `evidence` 字符串数组，同时新增 `evidence_refs`。

### 3.2 公告原文浏览与来源追溯

#### 3.2.1 后端 API

新增/增强：

```text
GET /api/evidence/{ticker}/{evidence_id}/pdf
GET /api/evidence/{ticker}/{evidence_id}/text
GET /api/evidence/{ticker}/{evidence_id}/source
```

为支持页码追溯，`extract_pdf_text` 改为返回按页文本列表：

```python
# 设计示意
pages: list[str] = [page.extract_text() or "" for page in reader.pages]
# 保存 text/{evidence_id}.txt 仍保留全文；另存 text/{evidence_id}.pages.json
# 或直接让 local_text_path 指向 pages.json，按需兼容旧字段
```

`EvidenceSnippet.page` 在抽取时根据句子所在页写入真实页码，而不是 `None`。

- `pdf`：使用 `FileResponse` 返回 `local_pdf_path`，`media_type="application/pdf"`，建议 `inline` 以便浏览器直接查看。
- `text`：返回 `{"evidence_id", "title", "source_url", "pages", "text_preview"}`；支持 `page` 查询参数返回指定页文本片段。
- `source`：返回结构化来源元数据，包括 `evidence_id`、`source_label`、`source_type`、`grade`、`confidence`、`announcement_date`、`url`、`local_pdf_path`、`local_text_path`、`snippets`、`data_gaps`。

安全约束：

- 所有路径必须通过 `evidence_ticker_dir(ticker).resolve()` 包含校验。
- 只允许读取本 ticker 目录内的 `documents/{evidence_id}.pdf` 和 `text/{evidence_id}.txt`。
- `evidence_id` 必须匹配 `[0-9a-f]{64}`。
- 不返回 `.env`、`data` 根目录、其他项目路径。

#### 3.2.2 前端交互

- 在“公告原文摘要”每张卡片增加：
  - 等级徽标：`A` 绿、`B` 蓝、`C` 琥珀、`D` 灰。
  - “查看原文 PDF”按钮，新窗口打开 `/yanqing/api/evidence/{ticker}/{evidence_id}/pdf`。
  - “查看文本”按钮，打开模态/抽屉显示文本预览与页码。
- 在“可用证据摘要”“证据链”“核心矛盾证据矩阵”“跟踪触发器仪表盘”中的每条证据引用，渲染为可点击的来源链接：
  - 显示 `来源 · 日期 · 页码 · 等级`。
  - 点击后打开对应证据详情/原文定位。

#### 3.2.3 历史数据回填

- 对已有 `index.json` 中没有 `grade` / `source_type` 的记录，在 `_normalize_evidence_record` 中按标题和现有元数据自动回填，不强制重新下载。
- 回填函数保持幂等：已有等级不覆盖；只有缺失字段时计算。

### 3.3 跟踪触发器连接精确证据

#### 3.3.1 数据结构

```python
class TrackingDashboardItem(BaseModel):
    trigger: str = "数据不足"
    status: str = "watch"
    why: str = "数据不足"
    evidence: list[str] = Field(default_factory=list)          # 兼容文本
    evidence_refs: list[EvidenceRef] = Field(default_factory=list)  # 新增
    next_check: str = "数据不足"
    invalidate_if: str = "数据不足"
```

#### 3.3.2 后端行为

- AI 新报告可原生输出 `tracking_dashboard[].evidence_refs`。
- 服务端 `_validate_snapshot_evidence` / 新增 `_validate_evidence_refs` 校验：
  - `evidence_id` 必须存在于快照 `evidence_library.items`。
  - `quote` 必须与对应 snippet/文本片段匹配；不匹配则丢弃该 ref。
  - 没有有效 ref 时，该项 `status` 降级为 `data_insufficient`，并保留说明。
- Fallback 生成器：
  - 从 `contradiction_matrix[].supporting_evidence_refs / opposing_evidence_refs` 继承。
  - 若没有 refs，用触发器关键词（如“现金流”“合同”“减值”）在证据库 snippets 中做包含匹配，生成 `EvidenceRef`。
  - 匹配不到则保持 `data_insufficient`。
- 状态映射建议：
  - `confirmed`：存在至少一条 A/B 级直接支持证据。
  - `watch`：只有间接证据或 C 级证据。
  - `data_insufficient`：无有效证据引用。
  - `invalidated`：存在明确反向证据且无正向支持证据。

#### 3.3.3 前端展示

- 每个跟踪卡片新增“关联证据”区域：
  - 显示 `等级徽标 + 来源 + 页码 + 引用句`。
  - 点击后跳转到原文 PDF/文本。
- 状态徽标与证据等级联动，避免高亮“已确认”但实际只有 D 级证据。

### 3.4 PDF 分页与阅读体验优化

#### 3.4.1 分页策略

在 `build_research_pdf_html` 中采用：

- `@page { size: A4; margin: 14mm 12mm 16mm; }`
- 封面 `.cover` 后强制分页。
- 主要章节（当前研判、核心矛盾证据矩阵、跟踪触发器仪表盘、财报字段追溯、可用证据摘要、证据链、公告原文摘要）使用 `break-before: page` 或 `.panel` 容器。
- `.panel`, `.card`, `.metric`, `.grid > article` 使用 `break-inside: avoid-page`。
- 长证据列表（公告原文摘要）允许容器跨页，但单个卡片不跨页；若卡片过高则内部可截断展示，完整内容通过原文链接查看。
- 每个 PDF 页底部显示报告标题和页码（若 Chromium 支持 margin boxes 则用 `@bottom-center`；否则通过分页脚本或页脚 HTML 实现降级方案）。

#### 3.4.2 内容组织

PDF 章节顺序保持与线上报告一致：

1. 封面/标题/关键指标
2. 核心观点
3. 当前研判
4. 基本研究框架
5. 核心矛盾证据矩阵
6. 跟踪触发器仪表盘
7. 系统识别的异常
8. 财报字段追溯
9. 可用证据摘要
10. 调研问题
11. 证据链
12. 公告原文摘要

每章内部不出现“标题在页尾、内容在下一页”的孤行。

#### 3.4.3 来源追溯页

PDF 中新增“证据来源追溯”小节（或并入公告原文摘要）：

- 按 `evidence_refs` 汇总所有被引用的证据。
- 每行显示：`等级`、`来源`、`日期`、`页码`、`引用句`、`evidence_id` 前 12 位。
- 让离线 PDF 仍可核对来源，而不是只有不可点击的文本。

### 3.5 测试与镜像同步前置项

当前发现：

- VPS 主机 `/root/apps/yanqing/backend/test_main.py` 与本地/bare 仓库一致。
- 运行容器 `/app/backend/test_main.py` 是旧版本，包含已删除的 `payload` 断言，导致容器内 `python -m unittest backend.test_main -v` 出现 1 个 error。
- 容器内 `main.py` 与主机一致，因此不影响生产运行，但影响“容器内测试全绿”的验证基线。

建议 Phase 0（需用户确认部署）：

```bash
cd /root/apps/yanqing
docker compose --env-file .env.production -f docker-compose.prod.yml up -d --build
```

验证：

```bash
docker exec brianhub-yanqing-app-1 python -m unittest backend.test_main -v
curl -fsS http://localhost:8000/api/health
```

如果用户暂不确认部署，Phase 0 可跳过，但后续 VPS 容器测试验证会受旧测试文件影响，需以本地/重建后的容器为准。

## 5. 验证方案

- 单元测试：
  - `grade_evidence_record` 对定期报告/公告/缺失字段给出正确等级。
  - `_normalize_evidence_record` 能幂等回填历史数据。
  - `_validate_evidence_refs` 拒绝不存在/引用不匹配的 evidence_id。
  - `tracking_dashboard` fallback 能生成/降级 evidence_refs。
  - 原文 PDF/text API 拒绝路径穿越和非法 evidence_id。
  - PDF HTML 包含分页 CSS 和来源追溯表。
- 容器测试：重建镜像后 `python -m unittest backend.test_main -v` 全绿。
- 集成验证：
  - 生成一份新深研报告，检查摘要/矩阵/跟踪看板中的等级徽标与原文链接。
  - 点击“查看原文 PDF”能打开 CNINFO 原始 PDF。
  - 导出 PDF 后检查分页、卡片断裂、来源追溯表。
  - 未登录访问新 API 仍由网关 SSO 302 保护。
